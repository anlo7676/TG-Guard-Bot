# 项目审查与修复（2026-09-07，v1.7.4）

## 审查范围

检查了管理员命令授权与目标解析、自动处罚与人工处理的衔接、通知失败重试、群审批撤销、数据库/Redis 机器人身份隔离、消息队列顺序与重试、验证取消和欢迎语清理、后台登录/CSRF，以及规则试判的异步状态。结合现有全量测试验证规则、AI 客户端和数据存储行为。本次不是形式化安全证明。

## 已修复问题

1. **高优先级：提示的管理员命令无法执行。** 原先只有 unban 接受数字 ID，ban/unmute 要求回复原消息，偏偏原广告已经删除。现在 warn、mute、ban、unmute、unban、kick 均支持数字 ID；mute 支持 /mute 用户ID 2h，保留回复消息用法。非管理员仍不能处罚。
2. **高优先级：通知失败可能重复禁言。** 原先持续禁言与通知共用 acted 标记，通知失败后会重新限制成员。现在禁言完成立即持久化 acted，通知失败只补通知。后续已完成的管理员封禁/解禁等决定会使旧待处理任务变为 skipped，避免旧任务覆盖新决定。
3. **中优先级：一次性登录链接过早消费。** 原先先 GETDEL 再创建会话，创建失败会浪费链接。现在在 Redis 单次脚本内先建立会话再消费票据；缓存故障提示服务不可用，保留可重试语义。保留一票一次、会话有效期、HttpOnly/SameSite/CSRF 校验。
4. **中优先级：试判结果与输入不一致。** 点击正常示例时清除旧转发来源/引用；编辑输入清除旧结果；晚返回的旧请求不覆盖新输入；请求失败清除旧结论。

## 验证

- Go 全量测试（含独立 _test MySQL 数据库、Redis 集成与模拟 Telegram）和 go vet 通过。
- JavaScript 语法检查及 12 项前端测试通过。
- 新增验收覆盖普通成员不能按 ID 解禁、管理员按 ID 封禁/解禁/限时禁言、禁言成功后通知失败、人工解禁后重放旧任务不再禁言或误发通知。
- 登录测试覆盖 Redis 故障后票据可继续使用、会话与票据状态一致、一票不可重放。
- 原有测试继续覆盖审批隔离、验证本人限制、超时恢复、欢迎语持久清理、广告前三次警告及第四次持续禁言。

## 仍需了解的边界

- Telegram 与 MySQL 无法组成事务：远端成功而本地完成标记尚未写入时崩溃，仍可能产生重复通知。已修复正常错误重试，不能承诺跨系统严格一次执行。
- 本地广告规则和举报前缀判断是启发式，无法理解全部引用/反诈语境，也可能被变形文本规避；没有 OCR。低于 AI 门槛的消息不会自动送 AI。
- 外部引用只分析 Telegram 实际提供的来源和片段，无法保证获得原文全文。
- 本次 superseded 判定依据机器人内已完成的人工命令记录；管理员直接通过 Telegram 客户端改权限的操作不一定有对应人工处罚记录。
- 自动违规次数沿用累计已完成处罚，不因人工解禁重置；解禁后再次违规仍可能立即禁言。当前行为已记录在项目策略中，未擅自清零历史记录。
- 欢迎语删除时间受 Telegram 网络和权限影响；重试耗尽的消息任务保留在失败队列，需排障后重试。
